# Feature Specification: 可恢复多 Agent 工作流

**Feature Branch**: `[003-durable-workflows]`
**Created**: 2026-09-12
**Status**: Draft
**Input**: User description: "为平台补齐 Task/Workflow State Store，使 Agent 可在异步子任务、回调、重启与扩缩容后可靠恢复。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 异步子任务后继续业务流程 (Priority: P1)

运营人员启动一条多 Agent 工作流。父 Agent 把分析工作交给子 Agent 后，平台在发送子任务前保存工作流现场，并把父工作流、当前步骤与子任务建立明确关联。父 Agent 无需占用执行资源等待结果。

**Why this priority**: 这是长时异步协作的最小闭环；没有它，子任务完成后系统无法可靠知道应恢复哪条流程和下一步。

**Independent Test**: 启动包含“需求分析 → 子 Agent 分析 → 生成方案”的工作流，在子任务运行期间停止父执行实例，再交付子任务结果；流程仍能从生成方案继续并保留完整历史。

**Acceptance Scenarios**:

1. **Given** 一条待执行工作流，**When** 父步骤创建异步子任务，**Then** 系统在对外发送前持久化父工作流状态、等待原因、下一步骤和子任务关联。
2. **Given** 父工作流正在等待子任务，**When** 子任务完成事件到达，**Then** 系统将结果写入对应工作流并只恢复一次后续步骤。
3. **Given** 父执行实例在等待期间重启或迁移，**When** 子任务完成事件到达，**Then** 任意健康执行实例均可从已保存现场恢复流程。

---

### User Story 2 - 可靠处理回调、重复与失败 (Priority: P1)

平台收到子 Agent 或受信任事件源发来的完成、失败或取消通知时，安全地识别其来源与关联任务。重复、乱序或迟到通知不会造成重复执行、跨租户恢复或已终止工作流复活。

**Why this priority**: 回调投递至少一次是常态；没有幂等和鉴权，工作流会重复产生副作用，或被错误事件影响。

**Independent Test**: 对同一已关联子任务连续提交重复完成通知、失败后重试通知与未知任务通知，验证只有第一条有效事件推进工作流，其余事件可审计但不重复执行。

**Acceptance Scenarios**:

1. **Given** 已登记的等待关联，**When** 收到经验证的完成通知，**Then** 系统记录接收结果并安排唯一一次恢复。
2. **Given** 已处理的事件标识，**When** 再次收到相同通知，**Then** 系统返回可识别的幂等结果且不再次推进流程。
3. **Given** 未知、来源不可信、租户不匹配或已终止工作流的通知，**When** 系统接收该通知，**Then** 不恢复任何工作流，并留下安全审计记录。

---

### User Story 3 - 运营人员观察和干预长时流程 (Priority: P2)

运营人员可在任务中心看到整条工作流、各步骤、关联子任务、等待原因、最近事件和下一步；在授权范围内可取消、重试可恢复步骤或在用户补充信息后继续暂停的流程。

**Why this priority**: 状态存储若不可见，就无法在超时、第三方故障或人工审批场景中可靠运营。

**Independent Test**: 创建包含等待、失败和用户输入暂停的工作流，验证授权运营人员可定位对应子任务、查看脱敏状态，并执行一次可审计的取消或重试。

**Acceptance Scenarios**:

1. **Given** 一条运行、等待、暂停或失败的工作流，**When** 授权用户查看详情，**Then** 可看到当前步骤、状态时间线、关联任务和可执行操作，而不会看到未授权凭据或其他租户数据。
2. **Given** 可重试的失败步骤，**When** 授权用户发起重试，**Then** 系统创建新的步骤尝试并保留原失败记录。
3. **Given** 用户输入暂停的工作流，**When** 所需信息被补齐，**Then** 系统从保存的下一步骤继续，而不重复已经完成的步骤。

---

### User Story 4 - 处理超时、取消和恢复队列 (Priority: P2)

平台主动识别长时间无响应、执行实例中断或等待期限到达的流程，并根据工作流策略进入重试、失败、取消或人工处理状态；恢复过程不会丢失已完成步骤。

**Why this priority**: 仅依赖回调会让丢失回调和执行实例故障永久卡住业务流程。

**Independent Test**: 让一个子任务超过等待期限、让一个恢复请求在执行中断后遗留，验证系统能生成明确状态并在可恢复时安全接手。

**Acceptance Scenarios**:

1. **Given** 超过等待期限且未完成的子任务，**When** 到达其恢复检查时间，**Then** 系统按策略将流程标为待重试、失败或待人工处理，并记录原因。
2. **Given** 已取消的父工作流，**When** 迟到的子任务结果到达，**Then** 系统保存必要审计信息但不执行后续业务步骤。

### Edge Cases

- 子任务在关联状态尚未对外发送时创建失败：父工作流不得停留在无法恢复的等待状态。
- 子任务结果先于网络响应到达：系统仍必须建立唯一关联并正确处理结果。
- 两个执行实例同时尝试恢复同一工作流：只有一个实例可获得该次恢复权，另一个不会重复运行步骤。
- 子任务返回的数据超出允许的保存范围或包含敏感字段：系统必须拒绝或脱敏该数据，并将流程置为可诊断的失败或人工处理状态。
- 工作流定义在实例运行期间被更新：已启动实例继续使用其启动时锁定的版本；新实例使用新版本。
- 父工作流或租户被删除、停用或失去权限：不得再调度新的子任务或恢复步骤。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持创建具备唯一标识、所属租户、定义版本、发起者、输入和生命周期状态的工作流实例。
- **FR-002**: 系统 MUST 将工作流实例与其步骤尝试、A2A 任务及相关事件建立可查询的关联，并保持租户隔离。
- **FR-003**: 系统 MUST 在创建或调度异步子任务前，原子保存父工作流的当前步骤、等待原因、下一步骤和恢复所需上下文。
- **FR-004**: 系统 MUST 支持工作流状态 `queued`、`running`、`waiting`、`input_required`、`completed`、`failed`、`cancelled` 和 `needs_attention`，并记录每次状态转换的时间、原因和操作者或事件源。
- **FR-005**: 系统 MUST 为每次子任务调度建立不可歧义的关联标识，使完成、失败、取消和超时事件能定位到唯一的步骤尝试和父工作流。
- **FR-006**: 系统 MUST 验证异步事件的事件源、租户、关联标识与完整性；无法验证的事件不得推进工作流。
- **FR-007**: 系统 MUST 将事件处理设计为幂等：同一事件或同一子任务的重复终态通知不得使同一后续步骤执行超过一次。
- **FR-008**: 系统 MUST 允许流程在等待子任务、等待用户输入或执行实例中断后释放当前执行资源，并由任意授权执行实例从持久化状态恢复。
- **FR-009**: 系统 MUST 在恢复前确认工作流仍处于可恢复状态、其定义版本有效且恢复权未被其他实例取得。
- **FR-010**: 系统 MUST 支持为等待步骤配置期限和失败处理策略，并为超时、不可恢复错误和重复恢复冲突提供明确、可查询的终态或人工处理状态。
- **FR-011**: 系统 MUST 支持取消工作流；取消后不得调度新的步骤，并应对仍在运行的关联子任务发出可追踪的取消请求。
- **FR-012**: 系统 MUST 记录不泄露秘密或隐藏推理的工作流时间线，包括步骤开始、等待、恢复、重试、终止和外部事件接收情况。
- **FR-013**: 授权用户 MUST 能按租户、状态、工作流类型、关联任务和时间范围检索工作流，并查看脱敏后的当前状态和历史。
- **FR-014**: 授权用户 MUST 能对允许人工干预的工作流执行取消、一次重试、继续已补齐输入或标记为已处理；所有操作必须审计。
- **FR-015**: 系统 MUST 对工作流上下文和子任务结果执行大小、保留期和敏感信息控制；秘密、访问令牌、未授权跨租户信息和隐藏推理不得被存入可见状态。
- **FR-016**: 系统 MUST 在服务恢复后发现到期等待、已领取但未完成的恢复工作和待处理事件，并安全地重新安排或标记它们。

### Key Entities *(include if feature involves data)*

- **工作流定义**: 某类业务流程的版本化步骤、允许状态、等待条件、期限和恢复规则。
- **工作流实例**: 一次具体业务执行的持久化现场，包含状态、当前步骤、下一步骤、受控上下文和定义版本。
- **步骤尝试**: 工作流中一次可审计的步骤执行，记录输入摘要、尝试次数、开始/结束时间、结果状态和错误摘要。
- **子任务关联**: 父工作流步骤与外部或内置 Agent 任务之间的唯一映射，包含等待状态、相关事件和终态。
- **恢复请求**: 一次可领取、可幂等、可追踪的继续执行请求，可能由完成事件、用户输入、超时检查或人工操作触发。
- **工作流事件**: 描述状态变化、外部通知、重试、取消和人工干预的不可变时间线记录。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在执行实例重启后，100% 已持久化且处于可恢复状态的测试工作流可在 60 秒内恢复或被明确标记为需要人工处理。
- **SC-002**: 对同一子任务连续投递 100 次相同完成通知时，后续业务步骤恰好执行 1 次，且每次重复通知均可被审计。
- **SC-003**: 在受控负载下，95% 已验证子任务完成通知会在 10 秒内反映为父工作流的状态更新或恢复尝试。
- **SC-004**: 授权运营人员可在 2 分钟内从一个子任务标识定位其父工作流、当前步骤、等待原因和最近一次恢复结果。
- **SC-005**: 100% 跨租户、未知关联、无效完整性或已终止工作流的测试通知均不会触发后续步骤。
- **SC-006**: 工作流取消后，100% 随后到达的测试结果不会触发新的业务步骤。

## Assumptions

- 首版复用现有租户、认证、任务中心、审计和事件通知能力；不改变现有 A2A Task 的协议权威性。
- 首版覆盖线性步骤与有向条件分支，支持父工作流等待一个或多个子任务；可视化拖拽编排编辑器不属于首版范围。
- 首版支持内置 Agent 与已注册远端 Agent 的异步协作；不要求平台托管或启动第三方 Agent 进程。
- 首版以受信任的任务订阅和签名回调作为外部唤醒来源，并保留人工恢复与超时扫描作为丢失通知的兜底。
- 首版工作流详情进入现有任务/运营界面；独立的流程设计器、计费和跨组织共享模板留待后续功能。
